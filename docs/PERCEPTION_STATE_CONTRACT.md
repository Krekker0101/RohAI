# Perception state contract

Версия: 3.0-vision, 27 сентября 2026.

## Основной инвариант

`UNKNOWN != EMPTY`. Достоверная очередь `0` разрешена только при полном пригодном наблюдении и завершённой оценке состояния. Недостоверные измерения сериализуются как JSON `null`, а не `0`. Ограниченная оценка скрытой очереди находится в отдельном `estimated_queue_count`; она не является входом adaptive-политики.

Это контракт программного конвейера, а не доказательство отсутствия физических автомобилей: детектор может пропускать объекты, а эвристики качества изображения имеют ложные срабатывания и пропуски. Отсутствие детекций само по себе не устанавливает статус OBSERVED.

## Доменная модель

`traffic_core.models.ObservationEvidence` передаётся в `ApproachState.observation` и `DirectionMetrics.observation`:

| Поле | Смысл |
|---|---|
| observation_status | OBSERVED, PARTIALLY_OBSERVED, DEGRADED, STALE, UNOBSERVED, FAILED |
| measurement_timestamp | Время кадра в шкале источника, секунды; не UTC и не часы контроллера |
| measurement_age_ms | Возраст кадра по monotonic clock с момента получения кадра процессом |
| source_camera_ids | Источники наблюдения; simulator — явно обозначенный точный источник симуляции |
| camera_health | Независимые именованные результаты проверок; false/неизвестное значение не подтверждает здоровье |
| visibility_score | Эвристический показатель пригодности ROI, не физическая доля видимой дороги |
| detection_coverage | Пригодность покрытия настроенных ROI, не измеренный recall детектора |
| tracking_quality | Консервативная оценка сохранности текущих треков |
| calibration_status | valid / missing / stale / invalid |
| measurement_confidence | Итоговая эвристическая оценка, обнуляемая при причинах недостоверности |
| failure_reasons | Машиночитаемые причины недостоверности |
| uncertainty | Раздельные detection, tracking, lane_assignment, motion, queue, observation confidence |

Статус OBSERVED без времени, источника, полной здоровой camera_health, действующей калибровки и положительной confidence не делает измерение достоверным. Явная simulator-evidence не имитирует физическую камеру. Модели нормализуют недостоверные значения в null. Неполный payload, объявленный OBSERVED, понижается до DEGRADED с `measurement_incomplete`. Проверка выполняется повторно при преобразовании в core state; safety дополнительно проверяет пригодность и наличие очереди.

| Статус | Пример | Поля измерений | Ограниченная оценка |
|---|---|---|---|
| OBSERVED | Проверки прошли, движение/остановка определены | Числа, включая настоящий измеренный ноль | Допустима |
| PARTIALLY_OBSERVED | Кратко скрытый ранее подтверждённый трек | null | Может сохраняться с затухающей уверенностью |
| DEGRADED | Низкая частота, неподтверждённое движение, плохая картинка, низкая confidence | null | Только при наличии удерживаемых треков |
| STALE | Истёк срок свежести кадра | null | Не разрешает управление |
| UNOBSERVED | Направление выключено или отсутствует evidence | null | Не подменяет измерение |
| FAILED | Разрыв камеры, отказ/остановка pipeline, просрочка heartbeat этапа | null | Не разрешает управление |

При нескольких причинах failure/stale могут иметь приоритет над частичной наблюдаемостью. Полный список причин сохраняется. После завершения источника старый кадр не продолжает выдавать пригодные измерения.

## Проверки восприятия

`PerceptionHealthMonitor.inspect` проверяет каждую настроенную автомобильную и пешеходную ROI. Проверяются соединение, возраст кадра, временной интервал между обработанными кадрами, замороженное изображение, чёрная/недоэкспонированная/переэкспонированная ROI, текстура/размытие, подозрение на крупное перекрытие, наличие достаточного числа пикселей ROI, inference/analytics liveness, наличие и срок калибровки.

Диагностика изображения работает на 320×180 grayscale; это ограничивает стоимость проверок и задаёт масштаб порогов текстуры. Обнаружение крупного перекрытия сравнивает текстуру ROI с первоначальным пригодным образцом. Оно **не гарантирует** обнаружение текстурированного перекрытия, неверно направленной камеры или всех видов смещения. Полностью статичная исправная сцена может сработать как frozen: это консервативный отказ, не доказательство неисправности камеры.

`VisionPipeline.observation()` обновляет возраст, связь и heartbeat даже без новых результатов анализа. Проверки выполняются также при получении текущего REST/WS состояния и до передачи состояния контроллеру. `captured_at` — время локального чтения; скрытая задержка внутри сетевой камеры/кодека без меток времени источника отдельно не измеряется.

`PerceptionHealthSettings` задаёт пороги: freshness 3 s, minimum FPS 0.8, frozen 3 s, stage timeout 3 s, уровни яркости, долю непригодных пикселей, пороги размытия и падения текстуры. Это начальные инженерные параметры прототипа, а не нормативы дороги; их следует проверять на целевой камере.

## Калибровка

В геометрию добавлены `calibration_validated_at` с timezone и `calibration_valid_for_seconds`. Дата из будущего или истёкший срок не подтверждают калибровку. Дата должна отражать реально выполненную проверку, а не автоматически обновляться при старте.

Каждому подходу нужны `waiting_zone`, `crosswalk_zone`, `exit_zone`. Старое `pedestrian_crossing` читается как совместимый источник геометрии пересечения, но само по себе не заменяет полную калибровку. Старые файлы камер оставлены без выдуманных зон и отметок валидации: поток доступен для диагностики, управление не разрешено. Полное отсутствие файла геометрии останавливает startup; молчаливой геометрии по умолчанию для отсутствующего файла нет.

Геометрическая проверка формы polygon не доказывает соответствие реальной дороге. Homography, поправка перспективы, физическая скорость и автоматическое доказательство актуальности ракурса не добавлялись.

## Скрытые треки и время

`TrackStateEstimator` различает CONFIRMED_VISIBLE, TEMPORARILY_OCCLUDED, PREDICTED, LOST, EXPIRED. Скрытый трек имеет `visible=false`; его bbox — последнее наблюдение, а не новая визуальная детекция. PREDICTED означает удержание оценки состояния, не точный прогноз координат.

Настройки `AnalyticsSettings`:

- `stop_confirmation_seconds=0.2`: подтверждение остановки по времени.
- `motion_window_seconds=0.5`: временное окно оценки движения; сглаживание также учитывает dt.
- `max_motion_gap_seconds=1.5`: предельный интервал для оценки скорости.
- `prediction_after_seconds=0.5`, `occlusion_hold_seconds=1.5`: переход к predicted и предел удержания очереди.
- `lost_track_seconds=3`: срок хранения трека; после него объект удаляется.
- `lost_uncertainty_seconds=5`: дополнительное окно неопределённости после истечения трека, привязанное к last_seen, а не числу кадров.
- `id_recovery_distance_px=25`: пространственный порог консервативного восстановления нового ID.
- `min_detection_confidence=0.25`, `jitter_tolerance_px=2`: пороги детекции и малого смещения в эталонных пикселях.

`slow_frames` и `max_observation_gap_seconds` сохранены для совместимости старой конфигурации; решение об остановке больше не использует frame count или старый gap как причину достоверного нуля. `consecutive_slow_frames` остаётся диагностическим счётчиком.

Один пропуск не обнуляет интервал ожидания. Удерживаемое ожидание является оценкой, а не подтверждённым наблюдением скрытого интервала. Confidence трека убывает с его возрастом. После hold очередь больше не удерживается; последующая неопределённость остаётся явной. После окончания uncertainty-window новая пригодная серия наблюдений без объектов может дать измеренный ноль; runtime после ранее защёлкнутого fault автоматически не возобновляет управление.

Восстановление ID допускается только при взаимно однозначном близком сопоставлении одного класса в пределах hold. Неоднозначные предложения не объединяются. ReID после длительного перекрытия, сложные перестановки близких машин и объединение камер не реализованы. Бюджеты памяти для треков, ID и aliases ограничены; их исчерпание является явной ошибкой, не скрытой очисткой счётчиков.

## Пешеходы

Состояния: pedestrian_waiting, pedestrian_crossing, pedestrian_clearing, pedestrian_unknown. Определяются текущей зоной; неоднозначные/неизвестные назначения не разрешают достоверное состояние. Ожидание начинается при входе в waiting_zone, сохраняется при допустимом восстановлении того же трека и прекращается при выходе из этой зоны.

Поля подхода: pedestrian_count_waiting, pedestrian_oldest_wait_seconds, pedestrian_mean_wait_seconds, pedestrian_arrival_rate, pedestrian_crossing_count; vision дополнительно передаёт clearing/unknown counts. Истории прибытия пешеходов и транспорта разделены. Это наблюдаемое ожидание с момента попадания в зону, а не время до первого появления человека в камере.

## Manifest модели

`configs/models/yolo26n.json` — явный manifest существующих upstream-весов; номер класса не является бизнес-классом. Он содержит model_id/version, architecture, SHA-256, dataset_version, class_names, class_id_mapping, domain_mapping, input_size, training_commit, created_at, supported_features и calibration_requirements.

`training_commit=unknown-upstream` честно обозначает неизвестный commit обучения; created_at относится к созданию manifest. При собственном обучении эти метаданные должны быть получены из воспроизводимого эксперимента.

При старте `YOLODetector.open` требует manifest, читает имена классов из загруженной модели, проверяет точное совпадение имён/ID, полноту domain mapping, hash весов, размер входа и объявленную поддержку detect. Несовместимость останавливает inference и приводит к существующему fault-поведению pipeline. Неизвестный ID результата также вызывает ошибку. Silent fallback на COCO отсутствует.

`DomainClass` — совместимый alias расширенного `ObjectKind`: car, bus, truck, motorcycle, bicycle, pedestrian, emergency_vehicle, unknown. Добавление emergency_vehicle в контракт не включает автоматический аварийный приоритет. Unsupported upstream classes явно размечены unknown и исключены из списка классов, запрошенных у детектора; это не утверждение об отсутствии таких объектов в сцене. Семантическую правильность явно заданного domain mapping должен подтвердить автор manifest — сравнение строк не доказывает правильность разметки датасета.

## Safety и совместимость

Adaptive-политика отклоняет непригодные входы. Решение о fallback принимает `SafetyController.accept_observation`:

1. До первого полного пригодного состояния система удерживает all-red; стартовый clearance отсчитывается после ожидания.
2. После начала доверенного управления потеря пригодности **любого** из четырёх подходов защёлкивает существующий all-red fault.
3. Последующее улучшение картинки или emergency-запрос fault не снимают; требуется новый runtime и повторное прохождение проверок.

Это существующий аварийный механизм демонстрационного проекта, не новая дорожная нормативная политика. Он не заменяет аппаратные ACK/watchdog и физическую проверку ламп.

`ready` и `/health/ready` сохраняют смысл готовности pipeline/API, чтобы диагностические данные оставались доступны. `control_ready` отдельно показывает допуск к управлению; endpoints переключения политики и emergency возвращают 503, если допуска нет. Calibration mode по-прежнему не включает green.

Реальная vision-телеметрия имеет **schema_version=3.0-vision**, поскольку nullable-измерения несовместимы с прежним обещанием чисел. Симуляция остаётся 1.0; отдельное точное presentation demo остаётся 2.0-vision. Существующий клиентский normalizer адаптирован к v3 только для достоверных числовых измерений. Недостоверное направление или null он явно отклоняет через уже существующий путь ошибки, не превращая в ноль; control_ready=false снимает доверие к сигналам. Новые UI-компоненты и функции отображения не добавлялись. Детальная диагностика неизвестных измерений доступна через REST/WS; визуализация отдельных неизвестных направлений потребует отдельной задачи интерфейса.

Для проверки: `.venv/Scripts/python.exe -m pytest tests/test_perception_reliability.py -q`. Результаты полного quality gate и повторного F01–F08 аудита находятся в `PERCEPTION_RELIABILITY_AUDIT.md`.
