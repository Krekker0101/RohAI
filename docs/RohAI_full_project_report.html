1. Резюме и назначение проекта

RohAI предназначен для прототипирования интеллектуального управления дорожным перекрестком. Система принимает либо детерминированный поток из симулятора, либо наблюдения из видеокамеры, переводит их в единый формат TrafficState, рассчитывает спрос на подходах и предлагает длительность текущей фазы. Перед отправкой команды сигнал проходит через независимый SafetyController.

Проект объединяет пять задач: моделирование транспорта, компьютерное зрение, принятие решения, безопасное управление сигналами и операторскую визуализацию. Важное архитектурное решение состоит в том, что восприятие и управление разделены: Vision Engine сообщает, что видит камера; контроллер решает, какую фазу желательно включить; safety-машина определяет, какую фазу разрешено включить.

Что система уже умеет

  • работать в DEMO без камеры, используя синтетические наблюдения и реальную control/safety-логику;
  • запускать simulation с фиксированным seed и воспроизводимым сравнением Fixed-Time и Adaptive;
  • обрабатывать файл, webcam, RTSP и synthetic source;
  • детектировать классы транспорта YOLO26 и отслеживать их ByteTrack;
  • определять подход, очередь, ожидание, arrivals и congestion по калиброванным ROI;
  • выдавать REST, WebSocket, MJPEG и dashboard React;
  • переводить систему в all-red при ошибке, stale source, EOF или остановке.

Что проектом не обещается

Это не сертифицированная система реального перекрестка. Симулятор не моделирует физику движения, а записанное видео не реагирует на сигналы. В проекте еще нет физического ESP32 adapter, ACK, watchdog, hardware-in-the-loop, размеченной выборки качества и собственного train pipeline.

Практический смысл: текущая версия хорошо подходит для демонстрации архитектуры и проверки программных инвариантов. Для реальной дороги потребуется отдельная инженерная, нормативная и аппаратная валидация.

Границы зависимостей

traffic_core не импортирует FastAPI, OpenCV, simulator или аппаратные библиотеки. Backend создает объекты через constructor injection. Vision adapter использует общую функцию расчета state из core, поэтому правила traffic score не дублируются внутри YOLO-обертки.

Camera / Video / RTSP / Synthetic
        -> Vision Engine -> TrafficState
Simulator -------------------------> TrafficState
        -> Decision Controller -> Safety Controller -> Hardware port
        -> FastAPI REST/WebSocket -> React Dashboard

Главное создаваемое ядро проекта — не одна нейросеть, а связка «наблюдение → нормализованное состояние → решение → безопасный исполнитель». Это правильная основа для последующего подключения обучаемой политики без смешивания ее с safety.

3. Полный поток данных

Simulation path

При старте SimulationEngine создает Simulator, TrafficController и SafetyController. На каждом шаге симулятор сначала продвигает очередь под предыдущим сигналом, затем формирует текущий TrafficState. Контроллер предлагает фазу и зеленую длительность. Safety-машина проверяет переход и только после этого формирует SignalState. Telemetry содержит traffic, lamps, decision, KPI и emergency.

Vision path

Vision Engine состоит из четырех worker stages: capture, inference, analysis и publishing. Между ними стоят bounded queues вместимостью один кадр. При перегрузке старые промежуточные данные отбрасываются, чтобы управление не опаздывало из-за очереди кадров. Стадии не блокируют ASGI event loop.

  1. Capture получает кадр и добавляет source id, stream epoch, frame id и timestamp.
  2. Inference запускает YOLO26 + ByteTrack и выдает normalized detections.
  3. Analysis назначает lane, проверяет ROI, скорость, stop line, очередь, ожидание и arrivals.
  4. Publishing строит overlay, JPEG и immutable latest snapshot.
  5. Vision runtime переводит snapshot в общий core state и передает его ObservedTrafficController.

DEMO path

DEMO не притворяется реальной камерой: его данные синтетические. При этом он использует настоящий SimulationEngine, настоящий decision и настоящий safety controller. Физический hardware demo runtime не получает, поэтому демонстрация безопасна для показа на ноутбуке.

Смысл timestamps: Vision использует время источника для аналитики, но backend control-clock независим. Медленная inference не должна уменьшать minimum green, yellow или clearance.

4. Математика состояния и метрики

Для каждого направления создается ApproachState. В него входят классовые counts, длина очереди, traffic score, среднее и максимальное ожидание, arrival rate и уровень congestion. Общий TrafficState требует ровно четыре направления: north, south, east, west.

Traffic score

Вес объекта зависит от класса: car = 1.0, bus = 2.5, truck = 2.0, motorcycle = 0.5, bicycle = 0.4, pedestrian = 1.0. Для очереди добавляется возраст самого старого ожидающего объекта, обычно с коэффициентом 0.05:

traffic_score = sum(class_weight for queued objects)
                + oldest_wait_seconds * waiting_weight

Это объяснимая эвристика: автобус и грузовик влияют сильнее легкового автомобиля, а длительное ожидание постепенно повышает приоритет. Это не оценка пассажиров и не learned value function.

Метрики симулятора

5. Симулятор и benchmark

traffic_simulator моделирует point queues FIFO. Прибытия генерируются как пуассоновские потоки для подходов и pedestrians. Seed делает поток воспроизводимым. Обслуживание зависит от headway и разрешающего сигнала. Координат машин, ускорения, длины автомобиля, spillback и реальной геометрии движения нет.

Почему paired comparison важен

Fixed-Time и Adaptive прогоняются на одном сценарии, seed, горизонте, timing и шаге 0.5 секунды. Поэтому различие KPI объясняется политикой, а не тем, что одному алгоритму случайно достался другой поток.

6. Decision Engine: алгоритмы управления

Текущий контроллер поддерживает две политики. Fixed-Time выбирает заранее заданную длительность зеленого. Adaptive выбирает длительность при входе в green на основе traffic score текущей фазы.

green = min(max_green,
             min_green + seconds_per_score * phase_score)

Фазы проходят циклически: north_south → east_west → pedestrian → north_south. Такой порядок обеспечивает обслуживание каждой фазы и снижает риск starvation при перекосе спроса. Пешеходная длительность задается отдельно.

Emergency priority

Оператор может задать автомобильное направление с TTL от 1 до 120 секунд. Последний запрос заменяет предыдущий. Emergency меняет желаемую фазу, но не перепрыгивает minimum green, yellow или clearance. После TTL цикл возвращается к нормальному режиму.

Что это за «AI» сейчас

Название Smart AI в dashboard обозначает адаптивное принятие решения по наблюдаемому спросу. В строгом смысле это rule-based heuristic controller. Здесь нет параметров, полученных оптимизатором, нейронной policy network, reinforcement learning, imitation learning или обучения по reward.

Это не недостаток архитектуры: прозрачную политику легче проверить и безопасно ограничить. Но в технической документации нельзя называть ее обученной моделью. Если в будущем появится ML-policy, она должна выдавать только предложение, а SafetyController должен сохранить право отклонить опасный переход.

7. Safety Controller и отказоустойчивость

SafetyController — самая критичная часть control path. Он является конечным автоматом, который единолично формирует сигнал. Допустимый порядок выглядит так:

ALL_RED -> GREEN -> YELLOW -> ALL_RED -> GREEN

Защищаемые инварианты

  • startup начинается с all-red не менее заданного интервала;
  • green не завершается раньше minimum green;
  • между транспортными фазами сохраняется yellow и all-red;
  • пешеходный green имеет собственный minimum и clearance;
  • в одном tick выполняется не более одного перехода;
  • время должно быть конечным и монотонным;
  • ошибка защелкивает состояние all-red до нового runtime;
  • hardware apply выполняется с bounded timeout.

Отказ и readiness

При ошибке модели, decoder, stale source, EOF или runtime система пытается применить all-red. Readiness становится 503, liveness остается 200, чтобы отделить живой HTTP-процесс от готового control pipeline. Автоматического возврата к green после fault нет: требуется явный перезапуск.

Сейчас исполнитель — MockHardwareController. Python-команда сама по себе не доказывает физическое состояние ламп. Для настоящей установки нужны подтверждение ACK, heartbeat, независимый watchdog на микроконтроллере и hardware-in-the-loop тесты запрещенных комбинаций.

Архитектурное правило: нейросеть и decision engine могут ошибаться или быть заменены. Safety слой не должен зависеть от того, каким способом получено наблюдение.

8. Vision Engine: YOLO26 и ByteTrack

Видеодетектор реализован в packages/vision/src/traffic_vision/detector.py. Загружается локальный файл datasets/models/yolo26n.pt. Перед inference выполняется warm-up. Ultralytics вызывается через model.track(..., persist=True) с конфигурацией ByteTrack и списком нужных COCO classes.

COCO idВнутренний класс
0person → pedestrian
1bicycle
2car
3motorcycle
5bus
7truck

Каждая detection содержит confidence, bbox, centroid/footpoint, timestamp и optional track ID. Неконфирмированные объекты могут отображаться, но не должны увеличивать счетчик arrivals. Повторные предложения с одним ID объединяются по максимальной confidence.

Идентичность и границы метода

Локальные IDs переводятся в монотонные session IDs, а публичный UID включает source и stream epoch. При reconnect или большом разрыве ByteTrack reset. Это не appearance re-identification: при перекрытии или смене ID одна машина может породить новый arrival. Поэтому уникальность гарантируется в рамках наблюдаемой session, а не навсегда.

ByteTrack — алгоритм ассоциации detections между кадрами, а не обучение модели. Он помогает получить траекторию и устойчивый ID, но не решает калибровку дороги, перспективу, скрытые объекты или причинность между сигналом и потоком.

9. Геометрия, ROI и аналитика очереди

Камера описывается JSON/YAML geometry. Координаты нормализованы в диапазон [0, 1], поэтому смена разрешения сохраняет поле зрения. Для подхода задаются incoming polygon, queue_zone, stop_line, optional pedestrian crossing, enabled и optional meters_per_pixel.

Назначение объекта

  1. Берется нижняя центральная точка bbox, то есть приближение точки контакта объекта с дорогой.
  2. Проверяется detection_zone и incoming ROI.
  3. Если несколько ROI подходят, новый объект получает UNKNOWN; прежняя lane сохраняется, если она остается допустимой.
  4. Stop line с upstream anchor определяет, находится ли объект до линии.

Подтверждение очереди

Транспорт считается queued, если он видим, назначен направлению, находится в queue ROI, находится upstream от stop line и движется медленнее порога несколько последовательных кадров. Скорость считается по смещению footpoint в reference pixels за секунду и сглаживается EMA. По умолчанию порог составляет 12 px/s, подтверждение — 3 slow frames, допустимый интервал — 0.75 s.

После подтверждения current wait растет. При движении или выходе из ROI текущий wait сбрасывается, а total observed wait сохраняется. Потерянный трек удаляется после TTL, но ID остается в counted set. Это защищает от повторного счета, хотя не исправляет ошибки самого tracker.

Queue length измеряется от stop line до дальнего края queued bbox. Без homography это pixels; при грубом meters_per_pixel — meters, но не точная физическая длина в перспективной сцене. Queue confidence — средняя confidence детекций, а не калиброванная вероятность правильной очереди.

10. Backend, API и Dashboard

Backend

FastAPI отвечает за lifespan, runtime task, REST endpoints, WebSocket, MJPEG, calibration, health и operator token. Один uvicorn worker обязателен, потому что camera state, tracker и controller принадлежат одному процессу. WebSocket хранит максимум один snapshot на клиента; медленный клиент пропускает промежуточные состояния, не блокируя управление.

Основные точки: /health/live, /health/ready, /api/v1/state, /ws/telemetry, /api/v1/vision/status, /api/v1/vision/frame.jpg, /api/v1/vision/stream и geometry GET/PUT. В control endpoints может требоваться X-Operator-Token.

Dashboard

Frontend в apps/dashboard написан на React 19, TypeScript и Vite. Интерфейс имеет страницы обзора, видеоаналитики, AI vs Fixed-Time и ROI calibration. Реализованы DEMO/REAL switch, WebSocket telemetry, emergency, policy switch, export JSON, выбор backend URL и operator token.

12. Что именно сейчас «обучено»

На основании исходников и документации корректный ответ такой: в проекте сейчас используется готовая предварительно обученная YOLO26n, но сам репозиторий не содержит процесса ее обучения или fine-tuning. Файл веса присутствует как готовый asset. Код выполняет inference и tracking, а не train.

В проекте отсутствуют

  • train script и dataset loader;
  • собственная разметка bounding boxes или track IDs;
  • train/validation/test manifests с фактическими данными;
  • optimizer, loss, epochs, checkpoints и scheduler;
  • precision, recall, mAP, ID-switch benchmark;
  • размеченный benchmark ошибки queue length;
  • обученная policy network для выбора сигналов;
  • reinforcement learning environment и reward optimization.

Что является уникальным в текущей реализации

Уникальность проекта сейчас находится прежде всего в инженерной связке, а не в уникальных весах модели: собственные контракты TrafficState, safety state machine, geometry-aware queue analytics, bounded pipeline, deterministic simulator, paired benchmark и dashboard. Synthetic detector — контролируемая fixture для тестов, не новая обученная модель.

Честная формулировка для презентации: «Мы интегрировали готовую YOLO26n с собственным tracking/geometry/queue pipeline и собственным safety-first контуром адаптивного управления». Нельзя утверждать, что YOLO26 обучена на уникальных данных RohAI, пока это не подтверждено экспериментом и артефактами обучения.

В документации datasets прямо сказано, что локальные датасеты и веса не входят в Git, а каталог описывает будущие правила хранения. Поэтому информации о размере собственного набора, числе классов, split, эпохах и качестве обучения в репозитории нет.

13. Как правильно обучить собственный ИИ

Этап A. Собственный vision dataset

  1. Собрать видео именно с целевых камер, разных сезонов, освещения, дождя, ночи, перекрытий и плотности потока.
  2. Не смешивать соседние кадры одного ролика между train, validation и test. Разделять по видео/сценарию.
  3. Разметить car, bus, truck, motorcycle, bicycle, pedestrian и при необходимости lane/queue attributes.
  4. Для tracking добавить consistent object IDs хотя бы на validation/test роликах.
  5. Для очереди разметить stop line, queue polygons и состояние queued/waiting; для физической длины добавить calibration/homography.
  6. Сохранить manifest, источник, лицензию, checksum, split и версию разметки в datasets/.

Этап B. Fine-tuning detector

Начинать следует с transfer learning от YOLO26n, а не с обучения с нуля. Подготовить конфигурацию классов, запустить несколько controlled experiments и сравнить baseline готовых весов с fine-tuned model на неизменном test set. Сохранять checkpoint, config, seed, commit hash и метрики.

Обязательные метрики: precision, recall, mAP50, mAP50-95 по каждому классу и отдельно по условиям. Для tracking: IDF1, MOTA/HOTA, ID switches и fragmentations. Для очереди: precision/recall queued objects, MAE/RMSE queue count и error estimated length.

Этап C. Проверка интеграции

После обучения detector нельзя автоматически объявлять control-ready. Сначала прогнать pipeline, затем replay с известными сигналами, затем closed-loop simulation. Сравнить false positives, missed vehicles, ID resets и задержку. Только после этого можно рассматривать улучшение decision policy.

14. Как обучать именно управление светофором

Если цель — сделать не только vision, но и обучаемый control AI, обучение должно идти в отдельном simulation environment. Safety нельзя отдавать нейросети. Policy должна получать state и предлагать действие: фазу, продление или длительность. SafetyController ограничивает действие допустимыми переходами.

Вариант 1: supervised / imitation learning

Сначала собрать эталонные решения из сильного rule-based optimizer или MPC на множестве сценариев. Обучить policy повторять действие учителя. Плюс метода — устойчивый старт и понятная проверка. Минус — модель наследует ошибки учителя.

Вариант 2: reinforcement learning

Определить observation: очереди, arrivals, waits, phase, elapsed, emergency state и confidence. Action ограничить небольшим набором допустимых продлений/переключений. Reward строить из уменьшения waiting, queue и остановок, с большими штрафами за starvation, unsafe request и нарушение fairness. Environment должен использовать разные seeds, demand patterns, missing detections и sensor noise.

reward = - alpha * total_wait
         - beta * queue_length
         - gamma * phase_switch_cost
         - penalty_for_starvation
         - very_large_penalty_for_unsafe_action

Оценивать policy нужно на новых seeds и сценариях, не только на тех, где она обучалась. Сравнение с Fixed-Time и текущей Adaptive heuristic должно быть paired и статистическим. Отдельно проверять worst-case, pedestrian fairness, emergency response и восстановление после sensor failure.

Приоритет: сначала сделать датасет и метрики perception, затем расширить simulator, затем обучать policy. Иначе будет невозможно понять, улучшение произошло из-за модели, симулятора или ошибки измерения.
